# 执行键、事务与安全重试

一次逻辑执行可以有多次尝试。`executionId` 标识持久账本，`executionKey` 用于识别相同业务意图，`attempt` 标识本次尝试；不能用随机日志 ID 作为下游去重键。

## 手动执行

`PUT /api/system/job/run/{jobId}` 可带 `Idempotency-Key` 请求头。同租户、同任务、同请求键返回同一执行回执；同一键不会因为 HTTP 重试而新建另一条执行。未传请求键时服务端生成新键，因此重新发起请求可能是另一项业务意图。

请求键允许 1–128 个字母、数字、点、下划线、冒号和短横线。存储键同时包含租户与任务 ID。页面在请求结果不确定时保留本次请求键，确认受理后再为下一次主动执行生成新键。

手动请求由持久队列交给 Quartz，HTTP 线程不直接执行业务。接口返回成功仅表示接收或返回既有回执，需查询 `/execution/{id}` 判断执行结果。

## 定时执行与恢复

定时逻辑键包含租户、任务 ID 与原计划触发时刻。恢复尝试沿用该时刻和键，而不是使用恢复节点的当前时间；同一计划即使再次触发也能识别为原执行。

账本的唯一约束和行锁负责 claim。进入业务前再次检查持有者、定义版本与租户。业务事务运行期间持有账本行锁，超期扫描跳过仍被锁定的尝试，避免长任务仅因超过租约就被另一节点重复执行。进程退出导致连接关闭后，未提交事务回滚，失联扫描才可以接管。

允许恢复的失联执行回到 `PENDING`，保留原键并增加尝试次数；未声明可恢复的执行转为 `FAILED`，需要先核对业务结果。Quartz 集群恢复与账本恢复可能先后到达，终态检查与当前持有者约束仍需生效。

## 哪些效果能一起提交

| 效果 | 一致性边界 |
| --- | --- |
| 当前 PostgreSQL 数据源、参与协调器事务的业务写入 | 与成功日志、`SUCCEEDED` 一起提交，异常一起回滚 |
| HTTP、邮件、短信、文件、其他数据源、业务主动开启的独立事务 | 不属于上述事务，须通过下游幂等键、事务消息或业务补偿处理 |

本地账本不能保证外部调用只发生一次。例如下游已处理成功、当前进程尚未提交就退出时，恢复会再次调用下游。下游应按原 `executionKey` 返回已有结果，或由业务 outbox 承接。确认这些条件后才启用 `recoverable=true`。

## 失败后重试

`PUT /api/system/job/execution/{id}/retry` 只允许当前配置版本下的失败执行，并满足以下之一：业务尚未获得执行尝试；任务明确声明可安全恢复。已经尝试过且未声明可恢复的失败任务不会开放重试。

列表和详情的 `retryable` 字段由服务端结合当前任务定义统一计算。配置已升级、任务已删除或执行已结束时，旧记录不再显示重试；任务曾声明 `recoverable=true` 本身不足以判定。调用重试接口仍需要 `system:job:edit`，服务端会在行锁下再次核验，不能依赖页面按钮作为授权。

重试沿用同一 `executionId` 和键；重新点击“立即执行”是新执行，两者意义不同。已成功或跳过的记录不会因调用 retry 再次执行业务。旧配置记录应保留审计信息，不能靠修改快照重新播放。

## Cron 错过触发策略

| 页面策略 | 值 | 行为 |
| --- | --- | --- |
| 按原计划补齐 | 1 | 使用 Quartz ignore misfires，可能连续补多个错过的计划 |
| 立即补一次 | 2 | 立即补一次，再按 Cron 继续 |
| 跳过过期触发 | 3 | 从后续计划继续 |

Cron 使用各节点的 JVM 默认时区；集群应统一 `user.timezone`。当前任务配置没有独立时区字段，UTC 三时点验收不涵盖 DST 切换。

升级前策略 1 与 2 实际均补一次，V34 将已有策略 1 转为 2，保留旧行为。选择策略 1 前应估算停机后的积压与外部依赖承受能力。

## 开发扩展

公共协议位于 `nz-common-job`：`JobExecutionCoordinator` 包装实际业务调用；`JobRunContext` 与 holder 传递并恢复执行上下文。Quartz starter 只依赖公共协议，业务持久实现由 `nz-job` 提供，框架不反向依赖 system。

自定义执行入口仍使用 `JobInvocation`，并传入正数任务 ID。保留的四参数构造方式用于兼容；业务不应自行伪造租户、恢复标记或 execution key 来绕过持久队列。
