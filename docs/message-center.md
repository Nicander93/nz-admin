# 站内消息中心

站内消息中心按租户保存逐用户消息，支持管理员发送、当前用户收件箱、未读数量、查看后自动已读、全部已读和删除。顶部导航在当前身份下维护一条通知连接，收到事件后重新查询数据库未读数，消息页同步刷新。连接跨页面保留，断线后使用新的一次性票据重连，并重读未读与历史；每 60 秒轮询作为兜底。

## 数据与权限

`sys_message` 每一行只属于一个租户和一个接收用户。MyBatis 租户拦截器负责租户行级隔离，业务服务继续校验当前登录用户必须等于消息接收人，避免通过消息 ID 越权读取或删除。

权限如下：

- `system:message:list`：收件箱与未读数量。
- `system:message:query`：查看本人消息详情。
- `system:message:read`：标记本人消息已读。
- `system:message:remove`：删除本人消息。
- `system:message:send`：向当前租户的启用用户发送消息。

管理员角色由 V17 自动获得上述菜单和按钮权限。普通角色需要在角色管理中显式授权。

## 接口

- `GET /api/system/realtime/notifications/ticket?transport=SSE`：申请仅本人消息的通知票据。
- `GET /api/system/message/page`
- `GET /api/system/message/{messageId}`
- `GET /api/system/message/unread-count`
- `PUT /api/system/message/{messageId}/read`
- `PUT /api/system/message/read-all`
- `DELETE /api/system/message/{messageId}`
- `POST /api/system/message/send`

发送范围支持当前租户全部启用用户或最多 500 个指定用户。指定用户中只要存在禁用、不存在或不属于当前租户的账号，整次发送就会失败。跳转地址只允许以单个 `/` 开头的站内路径，扩展数据必须是有效 JSON。

消息内容在前端按纯文本展示，不支持 HTML。这样可以直接阻断通过消息正文注入脚本；需要富文本时应增加独立的清洗和内容安全策略，不能直接改用 `v-html`。

## 迁移与运行边界

新库通过 `V17__message_center.sql` 建表和初始化权限；人工升级脚本是 `db/upgrade-p17-message-center.sql`。消息行采用逐接收人存储，因此已读和删除互不影响。

当前版本没有自动归档或保留期任务。数据规模增长后，应按业务合规要求新增前向 Flyway 迁移和独立清理任务。实时推送仅用于提升到达速度，收件箱数据库始终是事实来源；推送失败不会回滚已经提交的消息。

## 真实数据库与实时投递验证

`MessageLifecyclePostgresTest` 使用独立账号、租户和 Redis 前缀，验证收件箱、未读计数、已读幂等、删除与跨用户/跨租户拒绝。事务测试订阅真实 Redis：提交前不投递，提交后向对应接收人投递；回滚和第二条写入失败时不留部分消息，也不推送。跨节点在线 SSE 接收另由双节点脚本验证，消息历史仍由数据库保存。

## 通知连接与已读同步

通知通道只要求 `system:message:list`。它使用固定的 `USER_NOTIFICATIONS` scope，仅接受通过 `publishToUser` 定向给当前租户、当前用户的 `system-message` 与 `system-message-state`。租户广播、全局广播和测试台事件不能进入通知通道；实时测试台的 `GENERAL` scope 仍要求 `system:realtime:view`。

服务端在取票、消费、建立连接、每次投递和空闲复查时核对当前角色、菜单与套餐权限。账号身份和权限读取使用独立的只读事务，只看已提交数据；调用方的未提交修改或回滚不能提前撤销连接。事件过滤拒绝只丢弃事件，权限失效或无法核对时关闭连接。

已读、全部已读和删除在事务提交后向同一用户发布状态事件，其他标签页据此重查未读数。重复标记已读没有实际行变更时，不发布冗余事件。发送批次的任何插入失败或返回零行都会回滚整批，不能留下部分消息再宣称全部发送成功。

前端对后台失败安静重试；401 仍进入已有的会话过期处理。退出、切换身份或本地鉴权状态确认没有消息权限时，会取消连接、待处理请求和计时器；服务端撤权会关闭连接并拒绝新票据，前端后续的后台重试保持安静。迟到的旧请求与回调不能写入新身份的状态。未读数量始终取 API 结果，不根据推送条数累加。

## 节点升级

带 scope 的共享票据使用 `realtime:ticket:v2:` 命名空间。旧节点不能按旧键读取新通知票据，新节点也不会接受旧键，避免在混合版本中把通知连接降成可接收广播的通用连接。用户退出使用的共享撤销 epoch 继续跨节点生效。

部署应先完成所有后端节点升级，再发布启用通知通道的前端。跨版本取票与连接可能被拒绝，客户端需要重取票据；旧节点未退出前，不能把整个集群视为已具备新权限策略。无需清理业务 Redis 数据，旧票据按原 TTL 自行过期。
