# 新增迁移与已有环境升级

同一个变更要支持空库完整初始化和已有库向前升级。仓库使用连续 Flyway 版本，同时维护等价的手工升级脚本。

## 开发一条新迁移

1. 查看 `db/migration` 的最大版本，不凭记忆指定编号。
2. 新增下一版本 `V<版本>__<用途>.sql`，同时准备 `db/upgrade-p<版本>-<用途>.sql`。
3. 更新迁移资源测试登记与 README 声明，运行 `./nz migration check`。
4. 在空测试库执行全量迁移，并在上一版本副本执行增量升级。
5. 核对约束、索引、数据回填、菜单与套餐/角色映射。

已执行的 Flyway 文件有校验和，不能通过直接编辑历史文件修复已部署环境；追加迁移修复。

## 生产执行前

先备份并在副本演练，记录当前 `flyway_schema_history` 和应用版本。Flyway 自动迁移与手工升级二选一，不重复运行两条路径。使用 Flyway 的环境检查应用启动日志与历史表成功记录；无法使用 Flyway 的环境按版本依次执行手工脚本。

应用回滚不等于数据库结构回滚。旧应用必须兼容新结构，否则从备份恢复到独立实例后切换，不能用删除新增表的方法拼凑回滚。

## 验证失败的处理

先保存失败 SQL、当前迁移记录与日志，确认数据库是否存在部分执行或外部人工变更。不要为了启动成功关闭校验、清空历史表或重新导入 init.sql。

具体迁移约定见[数据库迁移原始手册](/database-migrations)，恢复步骤见[备份恢复](/operations/backup)。
