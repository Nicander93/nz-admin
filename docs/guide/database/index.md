# 数据库表设计

设计表时先确定租户、归属、唯一性和状态转换。生成器能读取字段并生成代码，但不能替你决定记录属于谁、谁可以修改它。

## 普通业务表的字段

| 字段 | 建议 | 作用 |
| --- | --- | --- |
| 主键 | PostgreSQL 单主键；类型按业务选择 | 生成器不支持复合主键 |
| tenant_id | 普通业务表使用 BIGINT NOT NULL | 接入数值租户拦截器 |
| dept_id | 业务需要部门范围时添加 | 数据权限部门维度 |
| owner_id / applicant_id | 选择并明确含义 | 记录归属或单据申请人 |
| status | 定义允许的转换 | 不能由通用更新任意修改 |
| create_time / update_time | 明确服务端写入方式 | 排序与审计 |

所属用户字段并不一定叫 owner_id，注册规则时填写真实列名。Warm-Flow 标准表使用字符串租户，由工作流专用隔离实现管理，不套普通 BIGINT 规则。

## 唯一约束按租户定义

用户名、业务编码等通常在租户内唯一，应把 tenant_id 纳入唯一键。全局唯一的标识要有明确业务理由。并发时“先查询不存在再插入”不能代替数据库唯一约束。

为分页查询、租户条件和业务关联建立符合真实访问模式的索引。不要仅因为字段存在就为每一列创建索引；用实际查询与测试验证。

## 两类登记都要做

租户规则决定跨租户不可见，数据范围规则决定同租户内可操作哪些记录。创建表后核对 `TenantTableRuleCustomizer` 与 `DataScopeRuleCustomizer`，或生成器输出的 AccessConfiguration 是否进入扫描。

启动租户表审计只能发现带租户列却没有登记的表，不能判断部门/归属规则是否符合业务。JDBC 操作也不会自动获得 MyBatis 条件。

## 建表与升级路线

使用新的连续 Flyway 迁移和对应手工脚本，不修改已执行的旧文件。代码生成器输出是代码起点；菜单 SQL 应整理进版本迁移，避免上线时靠人工散落执行。
